**Impact**: ~20/30 calls (67%) with LLM-based speaker detection are affected

### Root Cause 1: Gemini Audio Timeout (HIGH confidence)

**File**: `src/api/shared/durable_processing.py` lines 2203-2408
**Function**: `_diarize_with_gemini_audio()`

The function must complete ALL of this within a single 10-minute Azure Consumption Plan activity:
1. Download 41MB MP3 via httpx streaming (~1-2 min)
2. Upload to Gemini File API (~1-2 min)
3. Wait for Gemini to process the file (polling loop, up to 3 min)
4. `generate_content()` with 8-min timeout

For a 45-minute file, this chain exceeds 10 minutes. Additionally, `max_output_tokens: 32000` (line 2316) may truncate the output for a 45-min Arabic transcript (detected via `finish_reason.name == "MAX_TOKENS"` at lines 2338-2343, which returns `(None, None, None)`).

### Root Cause 2: GPT Arabic Sentence Splitting (HIGH confidence)

**File**: `src/api/shared/durable_processing.py` lines 2419-2716
**Function**: `_detect_speakers_with_gpt()`

The sentence-splitting regex at line 2467:
```python
raw_sentences = _re.split(r'(?<=[.!?¿¡。،])\s+', clean_text)
```
This fails on Arabic STT output which has **minimal punctuation** (ElevenLabs Scribe produces continuous text with few periods/question marks). When fewer than 5 "sentences" are detected, the function aborts early at lines 2484-2486:
```python
if len(sentences) < 5:
    logger.warning(f"[GPT Speaker] {call_id}: Only {len(sentences)} sentences, too few for detection")
    return None, None, None
```

Additional issues:
- Function was designed for Spanish (default `language_code="es"`, Spanish-specific examples in prompts)
- Noise filtering regex at lines 2449-2451 targets Spanish patterns (`la|de|da|na|ta|pa`)
- Arabic text should be split on `\n` in addition to punctuation

## Fix Plan for Next Session

### Fix 1: GPT Arabic Sentence Splitting (QUICK WIN - 15 min)

In `_detect_speakers_with_gpt()` at line 2467, add newline-based splitting for Arabic:

```python
# Current (fails on Arabic):
raw_sentences = _re.split(r'(?<=[.!?¿¡。،])\s+', clean_text)

# Fix: Also split on newlines and speaker label patterns
if source_language in ("ar", "auto"):
    # Arabic STT uses newlines as segment boundaries
    raw_sentences = _re.split(r'\n+|(?<=[.!?¿¡。،؟])\s+', clean_text)
else:
    raw_sentences = _re.split(r'(?<=[.!?¿¡。،])\s+', clean_text)
```

Also add Arabic question mark `؟` to the regex. And lower the minimum sentence threshold from 5 to 3 for Arabic.

### Fix 2: Gemini Audio for Long Calls (MEDIUM - 30 min)

Two approaches (choose one):

**Option A - Limit Gemini to short calls, improve GPT for long ones**:
```python
# In activity_enhance_speakers, only try Gemini for calls < 20 min
if sas_url and duration_seconds < 1200:  # 20 minutes
    enhanced_transcript, updated_speakers, method_used = _diarize_with_gemini_audio(...)
```
This is simpler and makes the GPT fallback the primary path for long calls (which is why Fix 1 must work first).

**Option B - Split Gemini into multiple activities**:
- Activity 1: Download + upload to Gemini File API (return file ID)
- Activity 2: Wait for processing + generate_content (use file ID)
This keeps each activity under 10 min but adds orchestrator complexity.

**Recommendation**: Option A is simpler and more reliable. Fix the GPT path for Arabic (Fix 1) to handle long calls, use Gemini only for short calls where it fits within the timeout.
