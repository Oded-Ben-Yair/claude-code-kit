## FIXES NEEDED TO REACH WORKING APP

### FIX 1 (P0 — CRITICAL): Rate limiter kills audio WebSocket

**Problem**: Browser sends ~10 audio chunks/second (100ms intervals). Network jitter causes bursts >15 msgs/sec. Current code CLOSES the WebSocket and BREAKS the loop, killing the entire session.

**File**: `backend/app/ws/audio.py` lines 101-105

**Current (BROKEN)**:
```python
# Rate limit check
if not connection_manager.check_rate_limit(conn):
    log.warning("ws_rate_limit_exceeded")
    await websocket.close(code=1008, reason="Rate limit exceeded")
    break
```

**Fix — change to**:
```python
# Rate limit check — drop chunk but keep connection alive
if not connection_manager.check_rate_limit(conn):
    log.warning("ws_rate_limit_exceeded_dropping_chunk")
    continue
```

**Why**: Drop the chunk silently and continue receiving. The connection stays alive, ElevenLabs keeps getting audio, transcription continues. Losing a single 100ms chunk is imperceptible; losing the entire WebSocket is catastrophic.

**Also consider**: Raising the rate limit from 15 to 20 msgs/sec in `backend/app/ws/manager.py` line 24:
```python
message_timestamps: deque = field(default_factory=lambda: deque(maxlen=20))  # was 15
```
And line 78:
```python
if len(ts) >= 20 and (now - ts[0]) < 1.0:  # was 15
```

### FIX 2 (P0 — CRITICAL): Sparse transcription — investigate audio gain and VAD

**Problem**: File upload produces 42 segments in 532 seconds (~1 segment/13s). Live browser mic produces 3 segments in 50 seconds (~1 segment/17s). The sparse output suggests the browser audio is either too quiet for Scribe's VAD or chunks are being lost.

**Investigation steps** (in order):
1. **Check browser audio gain**: Add logging in `backend/app/ws/audio.py` after receiving audio data to log the PCM amplitude:
   ```python
   import struct
   samples = struct.unpack(f'<{len(data)//2}h', data)
   peak = max(abs(s) for s in samples) if samples else 0
   if seq == 1 or seq % 50 == 0:
       log.info("ws_audio_level", peak_amplitude=peak, rms=int((sum(s*s for s in samples)/len(samples))**0.5))
   ```
   - If peak is consistently <500 (out of 32768), the mic audio is too quiet → need gain boost in AudioWorklet
   - If peak is >2000, audio level is fine → problem is VAD threshold

2. **Lower VAD silence threshold**: In `backend/app/services/elevenlabs.py` line 47:
   ```python
   "vad_silence_threshold_secs": "0.8",  # was 1.5 — try 0.8 first
   ```
   The 1.5 second silence threshold may be too aggressive for a conversation with natural pauses.

3. **Check chunks lost during rate-limit disconnects**: After fixing FIX 1, re-test. Many "sparse" segments may simply be chunks lost when the WebSocket died. Fix 1 may resolve much of this.

4. **AudioWorklet gain boost** (if needed): In `frontend/public/audio-processor.worklet.js`, add gain multiplication before sending:

   // After resampling, before sending
   const GAIN = 3.0; // Boost by 3x

### FIX 3 (P1): Language detection mis-identifies Gulf Arabic as Farsi

**Problem**: First committed segment returned `language_code: "fa"` (Farsi) instead of `"ar"` (Arabic). Gulf Arabic dialect has some phonetic overlap with Farsi.

**File**: `backend/app/services/elevenlabs.py` line 45

**Current**:
```python
"language_code": "ar",
```

**Options (pick one)**:
1. **Remove `language_code` entirely** — let Scribe auto-detect. Risk: slower first-segment detection.
2. **Keep `language_code: "ar"` AND ignore detected language in committed events** — always treat as Arabic for translation. This is the safest since we KNOW the input is Arabic.
3. **Add post-processing**: In `_handle_event` for `committed_transcript_with_timestamps`, override `language_code` to `"ar"` if `language_probability < 0.8`:
   ```python
   lang = msg.get("language_code", "ar")
   prob = msg.get("language_probability", 0.0)
   if lang != "ar" and prob < 0.8:
       logger.info("scribe_language_override", detected=lang, probability=prob)
       lang = "ar"
   ```

**Recommended**: Option 2 — always assume Arabic for translation. We control the input domain (Arabic sales calls). Don't trust per-segment language detection.
